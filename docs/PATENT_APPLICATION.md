## РЕФЕРАТ

Изобретение относится к области систем поддержки принятия инвестиционных решений с применением искусственного интеллекта. Раскрывается способ и система проведения инвестиционного комитета посредством мультиагентной дискуссии, в которой каждый аргумент представлен в виде структурированного шестипольного объекта (тезис / данные-основания / логическая связка / авторитет / числовая уверенность / условие ограничения), агенты располагают формализованными эпистемическими стойками (ROLE, PERSONAL, CRITIC, DOUBT), дискуссия формирует ориентированный ациклический граф аргументов с типизированными отношениями (CHALLENGES_WARRANT, SUPPORTS, CONCEDES_TO, RETRACTS, COMMITS_ON), противоречия между агентами обнаруживаются автоматически и разрешаются посредством T-синтеза в условия сделки (ConditionalDecision), а выходом системы является не бинарный вердикт, а формализованная модель условий финансирования, включающая трансевую структуру, сценарные расчёты и скелет смарт-контракта.

---

## 1. ОБЛАСТЬ ТЕХНИКИ

Изобретение относится к информационным технологиям, а именно к компьютерным системам поддержки принятия групповых решений в сфере инвестирования, использующим многоагентные архитектуры на основе больших языковых моделей (LLM) и формальные онтологии аргументации.

---

## 2. УРОВЕНЬ ТЕХНИКИ

### 2.1 Многоагентные системы для финансовых решений

Известны многоагентные системы для финансовой торговли и анализа, в частности система TradingAgents (arXiv:2412.20138, 2024), в которой агенты "бык" и "медведь" ведут дискуссию о рыночных позициях, а трейдер-агент синтезирует результат. Известна также система AlphaAgents (arXiv:2508.11152, 2025), применяющая агентов фундаментального, настроенческого и оценочного анализа для формирования портфеля.

Недостатки известных систем: отсутствие формальной онтологии аргументации, отсутствие типизированных эпистемических стоек агентов, отсутствие графа аргументов с хранимой линейкой обоснований, отсутствие механизма автоматического обнаружения противоречий и их разрешения в структуру условий сделки.

### 2.2 Формальные аргументационные онтологии в системах ИИ

Известно применение шестипольных аргументационных онтологий (тезис / данные / логическая связка / авторитет / уверенность / ограничение) в агентах типа BDI для формального вывода (Rodrigues et al., Theoretical Computer Science, 2019). Известно использование структурированных критических вопросов для управления рассуждениями LLM (arXiv:2412.15177, 2024). Известно применение аргументационных онтологий для автоматического извлечения структуры аргументов из текста (ACL 2024).

Недостатки: все известные применения аргументационных онтологий в системах ИИ решают задачи обработки естественного языка (argument mining) либо единичного вывода агента; ни одна система не использует шестипольную аргументационную онтологию как персистентную схему хранения аргументов в базе данных инвестиционного комитета.

### 2.3 Системы критического анализа инвестиционных решений

Известны коммерческие прототипы: система LinqAlpha на AWS Bedrock (2025), применяющая агента-критика для стресс-тестирования инвестиционных тезисов; система Virtual Investment Committee (GIC, Сингапур, 2025), генерирующая вопросы комитета по материалам сделки.

Недостатки: ни одна из известных систем не использует формальную шестипольную аргументационную онтологию, не имеет типизированных эпистемических стоек агентов, не строит граф аргументов с семантически типизированными отношениями, не реализует механизм T-синтеза противоречий в условия сделки.

### 2.4 Вывод

Таким образом, **совокупность существенных признаков заявляемого изобретения** — применение шестипольной аргументационной онтологии как персистентной схемы данных, формализованные эпистемические стойки агентов, граф аргументов с типизированными отношениями, автоматическое обнаружение противоречий и их T-синтез в ConditionalDecision со скелетом смарт-контракта — в уровне техники **не обнаружена**.

## 3. РАСКРЫТИЕ ИЗОБРЕТЕНИЯ

### 3.1 Технический результат

Технический результат заявляемого изобретения состоит в:
1. Обеспечении воспроизводимых и верифицируемых инвестиционных решений за счёт хранения полной линейки аргументов в графовой базе данных;
2. Повышении качества инвестиционного анализа за счёт применения формальной аргументационной онтологии, исключающей неструктурированные выводы языковых моделей;
3. Автоматическом преобразовании выявленных в ходе дискуссии противоречий в формализованные условия сделки (Term Sheet), снижающем трудозатраты на оформление инвестиционных документов;
4. Генерации скелета смарт-контракта для автоматического исполнения условий сделки;
5. Обеспечении аудитопригодности инвестиционного решения за счёт хранения полной истории дебатов в виде неизменяемого (append-only) графа событий.

### 3.2 Сущность изобретения

Способ автоматизированного проведения инвестиционного комитета включает следующие шаги:

**(A) Инициализация сессии.** Система создаёт объект сессии инвестиционного комитета, загружает данные рассматриваемого проекта (технологическая готовность TRL/MRL, финансовые показатели, рыночные данные, состав команды) и назначает множество агентов с функциональными ролями.

**(B) Назначение эпистемических стоек.** Каждый агент наделяется формализованной эпистемической стойкой из множества {ROLE, PERSONAL, CRITIC, DOUBT}, определяющей с какой позиции агент формирует аргумент: с позиции функциональной роли (ROLE), от личной позиции вне роли (PERSONAL), как намеренный критик-оппонент (CRITIC), или как агент, воздерживающийся от суждения ввиду недостатка данных (DOUBT).

**(C) Первичные позиции (фаза Opening).** Каждый агент генерирует первичный аргумент в виде структурированного объекта аргументационной онтологии. Объект аргумента включает поля: `claim` (тезис), `data` (данные-основания), `warrant` (логическая связка данных с тезисом), `backing` (авторитет/прецедент для warrant), `qualifier` (числовая уверенность 0–1), `rebuttal` (условия при которых тезис неверен), `epistemicStance` (эпистемическая стойка), `dimension` (измерение: trl/finance/team/market/sovereignty), `stance` (позиция: APPROVE/REJECT/DEFER).

**(D) Вычисление силы аргумента.** Для каждого аргумента вычисляется числовой показатель `argStrength` по формуле:

```
argStrength = qualifier + 0.1·[data≠∅] + 0.05·[backing≠∅] − 0.05·[rebuttal≠∅]
argStrength ∈ [0, 1]
```

**(E) Определение уязвимого компонента.** Для каждого аргумента определяется наиболее уязвимый компонент `weakestComponent` по приоритету: warrant → data → backing → claim, используемый для таргетированных атак.

**(F) Фаза перекрёстных дебатов (Cross-Debate).** Агенты генерируют аргументы следующих типов с типизированными семантическими отношениями к предшествующим аргументам:

| Тип аргумента     | Семантическое отношение          | Описание                              |
|-------------------|----------------------------------|---------------------------------------|
| CHALLENGE         | CHALLENGES_WARRANT / CHALLENGES_DATA / CHALLENGES_BACKING | Атака на конкретный компонент аргумента |
| COUNTER           | IS_RESPONSE_TO / CONTRADICTS     | Ответ на атаку                        |
| SUPPORT           | SUPPORTS                         | Поддержка позиции другого агента      |
| QUESTION          | CHALLENGES                       | Запрос разъяснения (directive speech act) |
| COMMITMENT        | COMMITS_ON                       | Условное обязательство сменить позицию |
| CONCESSION        | CONCEDES_TO + SUPPORTS           | Частичное признание правоты оппонента |
| RETRACTION        | RETRACTS                         | Отзыв собственного аргумента          |

**(G) Построение графа аргументов.** Все аргументы и типизированные отношения между ними сохраняются в графовой базе данных, образуя ориентированный ациклический граф (DAG) дебатов. Граф является append-only: ни один аргумент не изменяется и не удаляется.

**(H) Построение IBIS-графа разногласий.** Параллельно хронологическому графу аргументов строится тематическая карта по схеме Issue → Position → Argument. Issue (разногласие) фиксируется при каждом CHALLENGE-аргументе, все последующие COUNTER и SUPPORT привязываются к соответствующему Issue. IBIS-граф отражает тематическую структуру противоречий, независимо от хронологии дебатов.

**(I) Автоматическое обнаружение противоречий.** После завершения фазы Cross-Debate система выполняет алгоритм `detectContradictions`: для каждой пары аргументов с противоположными `stance` (один APPROVE, другой REJECT), принадлежащих разным агентам и имеющих одинаковое `dimension` или явную связь `CONTRADICTS`, создаётся объект Contradiction:

```
Contradiction = {
  thesis:    { agentId, argId, claim, stance: 'APPROVE' },
  antithesis: { agentId, argId, claim, stance: 'REJECT' },
  dimension: string,
  severity:  (argStrength_thesis + argStrength_antithesis) / 2
}
```

**(J) T-синтез: разрешение противоречий в условия сделки.** Для каждого выявленного противоречия система применяет метод `deriveConditionsFromContradictions` по схеме Т-проектности (Тезис ↔ Антитезис → Синтез-через-Условие). Для каждого измерения противоречия генерируется объект Condition:

```
Condition = {
  proposedBy:  agentId,           // агент, занявший позицию REJECT
  type:        MILESTONE | FINANCIAL | GOVERNANCE | TRANCHE | ...,
  priority:    BLOCKER | HIGH | MEDIUM | LOW,
  metric:      string,            // измеряемый показатель (trl, irr, ...)
  threshold:   number,            // пороговое значение
  deadline:    string,            // срок выполнения
  dealImpact:  { amountDelta, irrDelta, riskDelta, trancheFraction },
  resolves:    [contradictionId]  // какие противоречия снимает
}
```

**(K) Сборка ConditionalDecision.** Функция `assembleConditionalDecision` формирует выходной объект инвестиционного решения:

```
ConditionalDecision = {
  recommendation:    CONDITIONAL_APPROVE | APPROVE | DEFER | REJECT,
  contradictions:    [Contradiction],
  conditions:        [Condition],      // сортировка: BLOCKER → HIGH → MEDIUM
  dealTerms: {
    requestedAmount,
    adjustedAmount,   // с учётом dealImpact условий
    adjustedIRR,
    trancheStructure: [{ label, fraction, trigger }]
  },
  scenarios: {
    BASE:        { probability: 0.50, irr, exitYear },
    OPTIMISTIC:  { probability: 0.25, irr, exitYear },
    PESSIMISTIC: { probability: 0.25, irr, exitYear }
  },
  smartContractSkeleton: [{
    conditionId,
    IF:   "metric >= threshold",
    BY:   deadline,
    THEN: "releaseNextTranche() | flagMilestone()",
    ELSE: "notifyFund()"
  }]
}
```

**(L) Сохранение в базу знаний.** Функция `exportToKagEntities` преобразует объекты сессии, аргументов и IBIS-Issues в сущности базы знаний (KAG) для накопления прецедентов инвестиционных решений и обучения системы на исторических данных.

### 3.3 Трёхуровневая архитектура дискуссии

Система реализует трёхуровневую модель, разделяющую внутреннее состояние агентов, публичную коммуникацию и результирующие действия:

- **Уровень внутренних убеждений:** Внутреннее состояние агента — `agentBeliefs[id] = { internalScore, publicStance, confidence, driftHistory }`. Не передаётся другим агентам и не сохраняется в публичный граф.
- **Уровень коммуникации:** Структурированные аргументы, типизированные отношения, граф дебатов. Видимы всем агентам и хранятся в базе данных.
- **Уровень действий:** Голосование, формирование ConditionalDecision, интеграция с документами сделки (Term Sheet).

## 5. ОСУЩЕСТВЛЕНИЕ ИЗОБРЕТЕНИЯ

### 5.1 Аппаратно-программная среда

Изобретение реализуется на вычислительной системе, включающей:
- Сервер приложений с Node.js ESM-монолитом и Express HTTP-сервером;
- Графовую базу данных (NoSQL) с поддержкой типизированных объектов и отношений (Integram или аналог);
- Базу знаний с гибридным векторным и графовым поиском (KAG);
- Клиент-серверный интерфейс (Vue 3 / React) с визуализацией графа аргументов в реальном времени;
- Подключение к одному или нескольким API больших языковых моделей через унифицированный роутер.

### 5.2 Агентная конфигурация

Система поддерживает конфигурируемое множество агентов. Эталонная конфигурация включает шесть агентов:

| ID          | Роль                  | Байас     | Вес | Фокус                      |
|-------------|-----------------------|-----------|-----|----------------------------|
| tech        | Технический аналитик  | neutral   | 0.18 | TRL, MRL, производство    |
| finance     | Финансовый аналитик   | skeptic   | 0.20 | IRR, unit economics       |
| sovereignty | Эксперт суверенности  | neutral   | 0.18 | локализация, сертификация |
| risk        | Риск-менеджер         | pessimist | 0.17 | PMBOK-реестр рисков       |
| portfolio   | Стратег портфеля      | optimist  | 0.15 | синергии, сравнение       |
| critic      | Критический аналитик  | skeptic   | 0.12 | оспаривание допущений     |

Агент `critic` по умолчанию получает эпистемическую стойку `CRITIC`. Агенты с типом аргумента `QUESTION` автоматически получают стойку `DOUBT`.

### 5.3 LLM-оркестратор

Для каждого агента и каждой задачи система маршрутизирует запросы к оптимальной языковой модели по профилю (fast / balanced / quality). Маршрутизация учитывает: тип фазы, тип аргумента, сложность задачи. Распределение моделей записывается в граф событий (`MODEL_ASSIGNED`) для аудита.

### 5.4 Пример конкретного осуществления

**Задача:** принятие решения о финансировании UAV-стартапа с параметрами TRL=4, запрашиваемая сумма 150 млн руб., проектный IRR=28%.

1. **PRIMARY_POSITIONS:** Агент `tech` генерирует аргумент:
   ```
   claim:   "Рекомендую DEFER до достижения TRL=6"
   data:    "TRL=4, нет производственного партнёра"
   warrant: "Без TRL≥6 серийное производство невозможно в горизонте 2 лет"
   backing: "NASA TRL scale; прецедент Аэронет-2022 (3 проекта с TRL<5 не вышли)"
   qualifier: 0.82
   rebuttal: "если команда имеет трек-рекорд производства — пересмотреть"
   epistemicStance: ROLE
   stance: REJECT, dimension: trl
   ```
   Агент `portfolio` генерирует:
   ```
   claim:   "TAM=15 млрд руб., рынок военного БПЛА растёт → рекомендую APPROVE"
   data:    "Рост сегмента БПЛА Минобороны +340% за 2022–2024"
   warrant: "Крупный и растущий рынок компенсирует технологический риск раннего TRL"
   qualifier: 0.71
   rebuttal: "если конкуренты выйдут раньше — TAM сожмётся"
   epistemicStance: ROLE
   stance: APPROVE, dimension: market
   ```

2. **CROSS_DEBATE:** Агент `tech` атакует warrant аргумента `portfolio`:
   ```
   type: CHALLENGE
   relation: CHALLENGES_WARRANT → argument[portfolio.opening]
   attackedComponent: warrant
   claim: "Рынок не компенсирует TRL-риск без производственного плана"
   ```
   `argStrength(tech.challenge) = 0.82 + 0.1 + 0.05 - 0.05 = 0.92`

3. **detectContradictions:** Обнаружено противоречие:
   ```
   thesis:    { agentId: portfolio, claim: "TAM компенсирует TRL", stance: APPROVE }
   antithesis: { agentId: tech,     claim: "TRL=4 блокирует серию", stance: REJECT }
   dimension: trl
   severity: (0.71 + 0.92) / 2 = 0.815
   ```

4. **T-синтез → Condition:**
   ```
   type: MILESTONE, priority: BLOCKER
   text: "Достичь TRL=6 до начала Транша A (независимая экспертиза)"
   metric: trl, threshold: 6, deadline: "6 months"
   dealImpact: { trancheFraction: 0.3, riskDelta: -0.15 }
   ```

5. **ConditionalDecision:**
   ```
   recommendation: CONDITIONAL_APPROVE
   trancheStructure: [
     { label: "Транш A", fraction: 0.30, trigger: "Подписание" },
     { label: "Транш B", fraction: 0.70, trigger: "TRL≥6 + независимая экспертиза" }
   ]
   smartContractSkeleton: [
     { IF: "trl >= 6", BY: "6 months", THEN: "releaseNextTranche()", ELSE: "notifyFund()" }
   ]
   ```

## 6. ФОРМУЛА ИЗОБРЕТЕНИЯ

### Независимые пункты

**Пункт 1 (способ)**

Способ автоматизированного проведения инвестиционного комитета с использованием мультиагентной аргументационной онтологии, реализуемый вычислительной системой и включающий:

(а) инициализацию сессии инвестиционного комитета с назначением множества программных агентов, каждый из которых наделён функциональной ролью, весовым коэффициентом и формализованной эпистемической стойкой из множества {ROLE, PERSONAL, CRITIC, DOUBT};

(б) получение данных рассматриваемого проекта и генерацию первичных аргументов агентами, где каждый аргумент представляет собой структурированный шестипольный объект аргументационной онтологии, содержащий поля: тезис (claim), данные-основания (data), логическую связку (warrant), авторитет (backing), числовую уверенность (qualifier), условие ограничения тезиса (rebuttal);

(в) вычисление для каждого аргумента числового показателя силы аргумента (argStrength) на основе наличия и значений полей онтологии;

(г) проведение фазы перекрёстных дебатов, в ходе которой агенты генерируют аргументы типов CHALLENGE, COUNTER, SUPPORT, QUESTION, COMMITMENT, CONCESSION, RETRACTION с назначением каждому аргументу семантически типизированного отношения к целевому аргументу из множества {CHALLENGES_WARRANT, CHALLENGES_DATA, CHALLENGES_BACKING, IS_RESPONSE_TO, CONTRADICTS, SUPPORTS, CONCEDES_TO, RETRACTS, COMMITS_ON};

(д) построение и хранение ориентированного ациклического графа аргументов (DAG), в котором узлами являются аргументы, а рёбрами — типизированные семантические отношения, при этом граф является неизменяемым (append-only);

(е) автоматическое обнаружение противоречий посредством выявления пар аргументов с противоположными позициями (APPROVE / REJECT), принадлежащих разным агентам и имеющих совпадающее измерение анализа или явную связь противоречия, с вычислением показателя остроты противоречия (severity) как среднего значения показателей силы конкурирующих аргументов;

(ж) разрешение каждого выявленного противоречия посредством T-синтеза: генерации объекта условия сделки (Condition), содержащего тип условия, измеримый показатель (metric), пороговое значение (threshold), срок выполнения (deadline) и влияние на параметры сделки (dealImpact);

(з) сборку итогового объекта условного инвестиционного решения (ConditionalDecision), содержащего: рекомендацию, карту противоречий, массив условий сделки, трансевую структуру финансирования, сценарные расчёты (базовый, оптимистичный, консервативный) и скелет смарт-контракта с триггерами на измеримые показатели.

**Пункт 2 (система)**

Система автоматизированного проведения инвестиционного комитета с использованием мультиагентной аргументационной онтологии, содержащая:

— сервер приложений, выполненный с возможностью запуска оркестратора агентов и LLM-роутера;
— графовую базу данных для хранения ориентированного ациклического графа аргументов;
— модуль аргументационной онтологии, реализующий шестипольную схему структурирования аргументов;
— модуль эпистемических стоек, назначающий каждому агенту стойку из множества {ROLE, PERSONAL, CRITIC, DOUBT};
— модуль обнаружения противоречий, выявляющий пары конкурирующих аргументов;
— модуль T-синтеза, преобразующий выявленные противоречия в объекты условий сделки;
— модуль сборки ConditionalDecision, формирующий итоговый объект инвестиционного решения со скелетом смарт-контракта;
— пользовательский интерфейс с визуализацией графа аргументов и IBIS-карты разногласий в реальном времени.

## 7. ОПИСАНИЕ ИЗОБРЕТЕНИЯ (расширенное техническое)

### 7.1 Модуль аргументационной онтологии

Центральным элементом изобретения является модуль аргументационной онтологии, реализующий шестипольную схему структурирования аргументов как персистентную схему данных. В отличие от известных применений (argument mining в NLP, вывод в BDI-агентах), в заявляемой системе каждый аргумент является объектом базы данных со следующей схемой:

```javascript
{
  id:             string,           // уникальный идентификатор
  agentId:        string,           // агент-автор
  type:           ArgumentType,     // OPENING | CHALLENGE | COUNTER | ...
  ontotype:       OntologyEventURI, // 'argument:challenge' | ...
  epistemicStance: EpistemicStance, // ROLE | PERSONAL | CRITIC | DOUBT

  // Аргументационная онтология (6 полей)
  claim:    string,   // тезис
  data:     string,   // данные-основания
  warrant:  string,   // логическая связка
  backing:  string,   // авторитет/прецедент
  qualifier: number,  // уверенность в логике [0–1]
  rebuttal: string,   // условие ограничения тезиса
  text:     string,   // развёрнутое изложение (для отображения)

  // Производные (вычисляются системой)
  argStrength: number,       // сила аргумента [0–1]
  weakComponent:  string,    // уязвимый компонент
  relations:      Relation[],// семантические отношения к другим аргументам

  // Метаданные
  dimension: string,   // trl | finance | team | market | sovereignty
  stance:    string,   // APPROVE | REJECT | DEFER | UNKNOWN
  confidence: number,  // общая уверенность агента [0–1]
  model:     string,   // использованная LLM
  timestamp: Date,
}
```

### 7.2 Модуль T-синтеза

Модуль T-синтеза реализует преобразование противоречий в условия сделки по методологическому принципу: **противоречие является источником проектного решения**. Алгоритм:

1. Для каждого противоречия (thesis, antithesis, dimension, severity) определяется тип условия по dimension:
   - `trl` / `mrl` → `MILESTONE` (достижение технологической вехи)
   - `finance` → `FINANCIAL` (подтверждение финансовой модели)
   - `sovereignty` → `SOVEREIGNTY` (план импортозамещения)
   - `market` → `REPORTING` (письма о намерениях клиентов)
   - `team` → `TEAM` (усиление команды)

2. Инициатором условия назначается агент с позицией REJECT (блокирующая сторона).

3. `threshold` вычисляется из параметров проекта: для TRL — `max(project.trl + 2, 6)`.

4. `dealImpact` корректирует параметры сделки: `trancheFraction` определяет долю первого транша до выполнения условия.

5. Объект Condition содержит поле `resolves` — ссылки на снятые противоречия.

### 7.3 Механизм аудита

Граф аргументов является append-only: все объекты (аргументы, отношения, события) только добавляются и никогда не изменяются и не удаляются. Это обеспечивает:
- полный аудиторский след всех решений инвестиционного комитета;
- возможность воспроизведения дискуссии в любой момент времени;
- накопление прецедентов для последующего анализа;
- соответствие требованиям регуляторов к хранению инвестиционных решений.
