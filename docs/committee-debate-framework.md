# Фреймворк дебатов инвесткомитета ФСТ НТИ

## Цель документа

Описать теоретические основания, архитектуру агентов и дорожную карту развития
системы AI-дебатов на `/fst-committee`. Ориентир — дебаты, которые
**неотличимы от человеческих по динамике**, но превосходят их по глубине анализа.

---

## 1. Теоретические основания

### 1.1 СМД — Схема мыследеятельности (Щедровицкий, 1960–1990-е)

Три онтологических слоя, которые нельзя смешивать:

```
┌─────────────────────────────────────────────────────────────┐
│  МЫШЛЕНИЕ (М)          Чистая рефлексия. Агент внутри       │
│                        своей роли формирует позицию.        │
│                        Невидимо снаружи.                    │
├─────────────────────────────────────────────────────────────┤
│  МЫСЛЕКОММУНИКАЦИЯ     Речевые акты, аргументы, вызовы,     │
│  (МК)                  контраргументы. То что происходит    │
│                        в дебатах. ВИДИМО.                   │
├─────────────────────────────────────────────────────────────┤
│  МЫСЛЕДЕЙСТВИЕ (МД)    Голосование, протокол, решение.      │
│                        Переход от слов к действию.          │
└─────────────────────────────────────────────────────────────┘
```

Ключевое понятие: **позиция в роли**. Агент говорит не от себя —
он говорит с позиции функции (Юрист, Финансист, Критик). Личная позиция
(что он *на самом деле* думает) может отличаться от ролевой.

В контексте ИК ФСТ:
- М → `thinkingPhrases` + внутренний скоринг `agentScore()`
- МК → `session.arguments[]` + весь `_phaseCrossDebate()`
- МД → `_phaseVoting()` + `humanDecide()`

**Разрыв**: переход М→МК сейчас механистический. Агент не "думает" — он
сразу говорит. Нужен явный слой рефлексии перед речью.

---

### 1.2 Модель Тулмина (Toulmin, 1958)

Структура любого аргумента:

```
DATA (данные)  ──────────────→  CLAIM (утверждение)
                    │
               WARRANT (связь)
                    │
               BACKING (авторитет варранта)
                    │
               QUALIFIER (уверенность: probably / necessarily)
                    │
               REBUTTAL (известные исключения)
```

Пример для нашего ИК:
```
DATA:     TRL=4, нет производственного партнёра
WARRANT:  Без TRL≥6 серийное производство невозможно в горизонте 2 лет
BACKING:  NASA TRL scale, прецедент Аэронет-2022 (3 проекта с TRL<5 не вышли)
CLAIM:    Рекомендую DEFER до достижения TRL=6
QUALIFIER: вероятность успеха 30% (confidence: 0.30)
REBUTTAL: если команда имеет трек-рекорд производства — пересмотреть
```

Сейчас у нас только `text` + `confidence`. Тулмин даёт **анатомию** внутри.

---

### 1.3 Прагма-диалектика (ван Эмерен и Гроотендорст, 1984)

Четыре стадии критической дискуссии:

| Стадия | Функция | Соответствие в движке |
|--------|---------|----------------------|
| Confrontation | Фиксация разногласия | — (не реализовано) |
| Opening | Договор о правилах и ролях | `LOADING` → `PRIMARY_POSITIONS` |
| Argumentation | Обмен аргументами по правилам | `CROSS_DEBATE` |
| Concluding | Снятие разногласия | `FINAL_POSITIONS` → `VOTING` |

Типология речевых актов (Searle):
- **Assertive** — утверждение факта (`OPENING`, `CHALLENGE`)
- **Directive** — требование действия ("предоставить план...")
- **Commissive** — обязательство ("если TRL достигнет 6, поддержу")
- **Expressive** — оценочное суждение ("это серьёзная проблема")

**Разрыв**: все аргументы сейчас одного типа — assertive. Directive и
Commissive делают дебаты живыми ("если X выполнит Y — я меняю позицию").

---

### 1.4 IBIS — Issue-Based Information System (Rittel, 1970)

Граф решений из трёх типов узлов:

```
ISSUE (вопрос)
  └── POSITION (позиция-ответ)
        ├── PRO (аргумент за)
        └── CON (аргумент против)
```

Это **параллельная структура** к нашему графу событий. Разница:
- Граф событий: хронологический (что было сказано и когда)
- IBIS-граф: тематический (вокруг каких вопросов сформировались позиции)

**Применение**: после дебатов автоматически строить IBIS — сжатую карту
ключевых противоречий. Пример:

```
Issue: "Достаточен ли TRL=4 для первого транша?"
  Position A (Техн.аналитик): "Нет, нужен TRL≥6"
    PRO: прецеденты Аэронет
    CON (Стратег): "В портфеле есть успешные TRL=4"
  Position B (Критик): "TRL вообще не главный критерий — важна команда"
```

### 1.5 Эпистемические состояния

Классическая трёхчастная типология (эпистемология):

| Состояние | Определение | Пример в ИК |
|-----------|-------------|-------------|
| KNOWLEDGE | верифицированный факт | "TRL=4 указан в заявке" |
| BELIEF | убеждение (может быть ошибочным) | "рынок вырастет в 3 раза" |
| ADVOCACY | позиция в споре (≠ личное мнение) | дьявольский адвокат против |
| DOUBT | suspension of judgment | "данных недостаточно" |

**Разрыв**: агент голосует одним образом, но его речевые акты — другим.
Нет связи между тем что агент "утверждает" в дебатах и тем как голосует.

## 2. Текущая архитектура (as-is)

### Агенты

| ID | Роль | Байас | Вес | Фокус |
|----|------|-------|-----|-------|
| `tech` | Технический аналитик | neutral | 0.18 | TRL, MRL, производство |
| `finance` | Финансовый аналитик | skeptic | 0.20 | IRR, unit economics |
| `sovereignty` | Эксперт суверенности | neutral | 0.18 | 9D-матрица |
| `risk` | Риск-менеджер | pessimist | 0.17 | PMBOK-реестр |
| `portfolio` | Стратег портфеля | optimist | 0.15 | синергии НТИ |
| `devil` | Критический аналитик | skeptic | 0.12 | оспаривание допущений |

### Типы аргументов (онтология событий)

```
OPENING   → первичная позиция (assertive, М→МК)
CHALLENGE → атака на уязвимость (assertive, направленный)
COUNTER   → ответ на атаку (assertive, с targetArgId)
SUMMARY   → финальная позиция (synthesis)
```

### Отношения между аргументами

```
isResponseTo  → общий ответ
challenges    → прямая атака
supports      → поддержка чужой позиции
contradicts   → прямое противоречие
synthesizes   → обобщение серии аргументов
```

### Фазы сессии

```
IDLE → LOADING → PRIMARY_POSITIONS → CROSS_DEBATE
     → FINAL_POSITIONS → VOTING → SYNTHESIS
     → HUMAN_APPROVAL → CONCLUDED → RECOMMENDATIONS → REVISION
```

### Скоринг

Линейная взвешенная сумма нормализованных метрик проекта.
Каждый агент имеет свои `scoringWeights` — автономно от текста дебатов.

**Критический недостаток**: скоринг никак не влияет на аргументы,
и аргументы никак не влияют на скоринг. Два параллельных процесса.

## 3. Gap-анализ: что нужно для "человеческих" дебатов

### 3.1 Чего нет сейчас

| Феномен | В жизни | У нас |
|---------|---------|-------|
| Смена позиции под давлением | Агент меняет мнение после сильного аргумента | Нет — скоринг детерминирован |
| Условное обязательство | "Если покажут план — поддержу" | Нет |
| Коалиции | Два агента объединяются против третьего | Случайно, не структурно |
| Вопросы | "Можете объяснить как вы считали IRR?" | Нет — только утверждения |
| Признание правоты | "Согласен с коллегой в части суверенности" | Нет |
| Молчание / пауза | Агент пропускает раунд (не знает что сказать) | Нет — все всегда говорят |
| Рефлексия | Агент переосмысливает собственный аргумент | Нет |
| Разрыв позиция/голосование | Говорил за, проголосовал против | Нет — связано скорингом |

### 3.2 Почему дебаты кажутся механистическими

1. **Нет памяти внутри сессии**: каждый аргумент пишется с нуля, агент
   не "помнит" что сам говорил 3 реплики назад
2. **Нет реакции на силу аргумента**: слабый и сильный аргумент
   получают одинаковый ответ
3. **Нет динамики уверенности**: `confidence` назначается LLM в момент
   генерации, не эволюционирует
4. **CHALLENGE всегда случайный**: атакует random OPENING, а не самый
   уязвимый аргумент
5. **Нет модерации**: никто не суммирует противоречия, не задаёт
   следующий вопрос для обсуждения

## 3.5 Т-схема проектности (Переслегин)

**Ключевой инсайт**: противоречие — не помеха, а ИСТОЧНИК проекта.
Нет противоречия → нет проекта, есть только оптимизация.

Переслегин (Сергей Переслегин, российский методолог, ученик школы Щедровицкого):
> "Проект — это способ разрешить противоречие, которое нельзя разрешить
> эволюционным путём."

Т-схема проектности:
```
        ТЕЗИС (агент A: APPROVE)
       /
ПРОТИВОРЕЧИЕ                    → СИНТЕЗ (условие снимает противоречие)
       \
        АНТИТЕЗИС (агент B: REJECT)
```

**Пример**:
```
Тезис:     Стратег: "TAM=15млрд, рынок огромный → APPROVE"
Антитезис: Техн.аналитик: "TRL=4, нет серийного производства → REJECT"
Синтез:    CONDITIONAL_APPROVE:
             Условие: "Транш A (30%) сейчас.
                       Транш B (70%) — после TRL≥6 (независимая экспертиза, Q3 2025)"
```

Это не компромисс (50/50) — это **новая позиция**, которой не было ни у одного
из агентов до дебатов. Именно так работает умный ИК.

**Почему текущая система неживая**: скоринг вычисляется из метрик ДО дебатов.
Дебаты не меняют голос. Итог детерминирован. Это не дебаты — это оглашение
заранее вычисленного результата. Голосование 5 раз = 5 одинаковых результатов.

**Решение**: дебаты должны обнаруживать противоречия → противоречия порождают
условия → условия собираются в модель сделки → модель сделки — это выход ИК.

## 3.6 ConditionalDecision — цифровой двойник сделки

Выход ИК — не `recommendation: 'APPROVE'`, а:

```js
ConditionalDecision {
  recommendation: 'CONDITIONAL_APPROVE'

  contradictions: [
    { dimension: 'trl', severity: 0.85,
      thesis:     { agentId: 'portfolio', claim: 'рынок перевешивает TRL' },
      antithesis: { agentId: 'tech',      claim: 'TRL=4 блокирует серию' },
      status:     'RESOLVED_BY_CONDITION' }
  ]

  conditions: [
    { type: 'MILESTONE',  priority: 'BLOCKER',
      text: 'TRL≥6 до Транша B',
      metric: 'trl', threshold: 6, deadline: '6 months',
      dealImpact: { trancheFraction: 0.3 } },
    { type: 'GOVERNANCE', priority: 'HIGH',
      text: 'Наблюдатель фонда в совете директоров',
      dealImpact: { riskDelta: -0.08 } }
  ]

  dealTerms: {
    requestedAmount: 150_000_000,
    trancheStructure: [
      { label: 'Транш A', fraction: 0.3, trigger: 'Подписание' },
      { label: 'Транш B', fraction: 0.7, trigger: 'TRL≥6 + независимая экспертиза' }
    ]
  }

  scenarios: {
    BASE:        { probability: 0.50, irr: 28, exitYear: 5 },
    OPTIMISTIC:  { probability: 0.25, irr: 36, exitYear: 4 },
    PESSIMISTIC: { probability: 0.25, irr: 19, exitYear: 7 }
  }

  // Скелет смарт-контракта
  smartContractSkeleton: [
    { conditionId: 'cond_001',
      IF:   'trl >= 6',
      BY:   '6 months',
      THEN: 'releaseNextTranche()',
      ELSE: 'notifyFund()' }
  ]
}
```

**Это и есть цифровой двойник сделки**: параметры + условия + сценарии.
При выполнении условий → сценарий обновляется → новый ИК не нужен,
смарт-контракт сам переходит в следующий транш.

## 4. Дорожная карта обогащения

### Этап 1 — Toulmin: анатомия аргумента

**Что меняется**: структура объекта аргумента + промпт LLM

```js
// Было
{ text, type, confidence, dimension, stance }

// Станет
{
  text,       // полный текст для отображения
  claim,      // тезис (1 предложение)
  data,       // данные/основание
  warrant,    // логическая связь данных с тезисом
  qualifier,  // степень уверенности в логике (0–1)
  rebuttal,   // "но если..."
  type, confidence, dimension, stance
}
```

**Новый промпт** (дополнение к существующему):
```
Сформируй аргумент в структуре:
- claim: одно утверждение (тезис)
- data: конкретные данные из заявки
- warrant: почему эти данные поддерживают тезис
- qualifier: уверенность 0.0-1.0
- rebuttal: при каких условиях тезис неверен
- text: полное связное изложение (2-3 предложения)
```

**Что даёт**:
- Граф становится читаемым: видна логическая цепочка, а не просто текст
- CHALLENGE можно таргетировать на слабый `warrant` конкретного аргумента
  (а не на случайный OPENING)
- `rebuttal` естественно порождает COUNTER следующего агента

**Файлы**: `fstCommitteeAI.js`, `fstCommitteeOntology.js`, `DebateGraphPanel.vue`

### Этап 2 — Эпистемический статус + позиция в роли (Щедровицкий)

**Что меняется**: агент получает три слоя состояния

```js
// Новое поле в аргументе
epistemicStance: 'ROLE' | 'PERSONAL' | 'DEVIL_ADVOCATE' | 'DOUBT'

// Новое состояние агента в сессии
agentBeliefs: {
  [agentId]: {
    internalScore: 0.72,      // что агент реально думает (М-слой)
    publicStance: 'APPROVE',  // что говорит в дебатах (МК-слой)
    confidence: 0.85,
    driftHistory: [0.72, 0.68, 0.61]  // как менялась позиция под давлением
  }
}
```

**Механика дрейфа позиции**:
```
При получении аргумента с qualifier > 0.8 и stance != моей:
  internalScore += delta * (1 - моя_уверенность)
  → если delta достаточна → агент может поменять голос
```

**Типы речевых актов** (добавить к `ARGUMENT_TYPES`):
```js
QUESTION:    'QUESTION',     // "Как вы считали IRR?"
CONCESSION:  'CONCESSION',   // "Согласен в части X, но..."
COMMITMENT:  'COMMITMENT',   // "Если Y — изменю позицию"
RETRACTION:  'RETRACTION',   // агент отзывает свой аргумент
```

**Коалиции**: если два агента имеют `stance === 'REJECT'`, они
автоматически получают `coalition: 'bear'` — Критик + Риск-менеджер
могут объединиться в скоординированную атаку.

**Файлы**: `FstCommitteeEngine.js`, `FstCommitteeConfig.js`,
`fstCommitteeOntology.js`, `fstCommitteeAI.js`

### Этап 3 — IBIS-граф как тематический слой

**Что добавляется**: параллельно хронологическому графу событий строится
тематическая карта Issue → Position → Argument.

```js
// Автоматически извлекается из дебатов после CROSS_DEBATE
ibisGraph: {
  issues: [
    {
      id: 'issue_trl',
      text: 'Достаточен ли TRL=4 для первого транша?',
      raisedBy: 'tech',
      positions: [
        {
          agentId: 'tech',
          text: 'Нет, нужен TRL≥6',
          stance: 'REJECT',
          pros: ['arg_001'],
          cons: ['arg_004']
        },
        {
          agentId: 'portfolio',
          text: 'Критерий TRL не абсолютен при сильной команде',
          stance: 'DEFER',
          pros: ['arg_007']
        }
      ]
    }
  ]
}
```

**Как строить**: после каждого CHALLENGE — LLM извлекает Issue
из текста вызова (1 вопрос). Все последующие COUNTER и SUPPORT
привязываются к этому Issue.

**Визуализация**: отдельная вкладка "Карта разногласий" рядом с
"Графом событий" — показывает не когда что было сказано, а
**вокруг чего** идут споры.

**Файлы**: новый `fstCommitteeIBIS.js`, новый `IBISMapPanel.vue`,
`FstCommitteeEngine.js`

### Этап 4 — ConditionalDecision: Т-схема Переслегина

**Что меняется**: выход ИК — модель условий сделки, не бинарный вердикт

**Шаг 1 — detectContradictions(args)**
После CROSS_DEBATE автоматически находит пары аргументов:
- разные агенты с противоположным stance (APPROVE vs REJECT)
- одинаковое dimension (оба о TRL, или оба о финансах)
- severity = среднее toulminStrength обоих (чем увереннее оба → тем острее)

**Шаг 2 — deriveConditionsFromContradictions(contradictions, project)**
Для каждого противоречия генерирует Condition:
- Кто был против → тот предлагает условие
- Условие имеет: metric + threshold + deadline (→ смарт-контракт)
- dealImpact: как условие меняет параметры сделки

**Шаг 3 — assembleConditionalDecision()**
Собирает итоговый ConditionalDecision:
- Если есть BLOCKER-условия → `CONDITIONAL_APPROVE` (не просто APPROVE)
- trancheStructure из условий (30% сейчас, 70% после вехи)
- scenarios: BASE / OPTIMISTIC / PESSIMISTIC
- smartContractSkeleton: IF metric >= threshold BY deadline THEN action

**Шаг 4 — Дрейф позиций (ключевое)**
Дебаты должны менять скоринг:
```js
// В _agentSpeak: после каждого COUNTER/CHALLENGE
// если toulminStrength входящего аргумента > 0.8:
agentBeliefs[agent.id].internalScore += delta * (1 - агент.уверенность)
// → при достаточном дрейфе agentScore() пересчитывается
// → голос меняется: агент может перейти из REJECT в DEFER
```

**Шаг 5 — Интеграция с FstDeal**
ConditionalDecision.dealTerms → автозаполнение в FstDeal:
- conditions → Term Sheet
- trancheStructure → финансовая модель
- smartContractSkeleton → основа цифрового двойника сделки

**Файлы**: `fstCommitteeOntology.js` (уже добавлено),
`FstCommitteeEngine.js` (detectContradictions после CROSS_DEBATE),
`FstCommittee.vue` (новая вкладка "Условия сделки"),
`fstApi.js` (сохранение ConditionalDecision в Integram)

## 5. Целевая модель: "умные человеческие дебаты"

### Как выглядят настоящие умные дебаты

```
1. Каждый начинает с позиции (OPENING) — но уже зная позиции других
2. Кто-то задаёт острый ВОПРОС (а не утверждение)
3. Ответ на вопрос порождает COMMITMENT ("если X — то поддержу")
4. Другой агент атакует WARRANT, а не CLAIM (умная критика)
5. Под давлением агент делает CONCESSION (частичное согласие)
6. Образуется коалиция "за условное одобрение"
7. Критик оспаривает коалицию — открывает новый Issue
8. Голосование отражает эволюцию позиций, а не начальный скоринг
```

### Принципы которые должны быть заложены в промпты

**Принцип неоднозначности**: у каждого проекта есть аргументы с обеих
сторон. Агент, который видит только плюсы или только минусы — плохой агент.

**Принцип специфичности**: общие слова ("хорошая команда") слабее
конкретных данных ("основатель — автор 3 патентов в области БПЛА").

**Принцип реактивности**: следующий аргумент должен РЕАГИРОВАТЬ на
предыдущий — не игнорировать его.

**Принцип уязвимости**: агент должен признавать слабые места
своей позиции (`rebuttal`), иначе позиция выглядит манипулятивной.

**Принцип дрейфа**: позиция, которая не меняется под давлением
сильных аргументов — это упрямство, не экспертиза.
